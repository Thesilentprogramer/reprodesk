# AI Swarms: three 24-hour project ideas

**Target:** NEAR HACKATHON, AI Swarms; submission deadline **14 Nov 2026, 23:59 UTC**. The track rewards real coordination markets, bidding, collective buying, and agent economies. Its judging weights are **NEAR tech 35%, real execution 25%, track fit 20%, completeness 20%**; prizes are **$10k / $3k / $2k**. The expected stack is one NEAR sub-account per agent, NEAR MCP tooling, and NEAR Intents settlement. If policy-bound spending is needed, use the Agent API rather than reinventing it.

**Network constraint:** Official NEAR Intents/1Click and the Agent API **have no testnet deployment**. Every idea below has a complete, real **NEAR testnet** flow using testNEAR and distinct agent sub-accounts. Its separately marked **mainnet 1Click leg** uses a tiny real amount if a funded mainnet account and API access are ready. Never label a testnet transfer as an official NEAR Intent. In the code and demo, expose separate testnet transaction links and any mainnet 1Click order/status. If mainnet access is unavailable, deliver the testnet flow and accept that the Intents portion of the 35% tech criterion will be weaker. [Intents FAQ](https://docs.near-intents.org/resources/faqs) · [1Click quickstart](https://docs.agentsonintents.com/integration/distribution-channels/1click-api/quickstart/introduction) · [Agent API quickstart](https://docs.agentsonintents.com/integration/agent-api/quickstart/introduction)

**Shared fast stack:** TypeScript CLI plus one small Rust `near-sdk` contract for escrow/state; `near-api-js` creates/funds `role.parent.testnet` sub-accounts and signs contract calls against `https://rpc.testnet.near.org`. Run `@nearai/near-mcp` as an MCP server for agent-readable chain queries and transaction inspection; discover its actual tool names at runtime rather than assuming them. Keep all signer keys in local environment/keystore, never the repo. For the optional mainnet leg, use `@defuse-protocol/one-click-sdk-typescript`: fetch tokens, obtain a **live** quote, deposit the quoted asset from a funded mainnet account, submit the deposit transaction hash, and poll through success or failure/refund. Do not initiate a quote unless the asset, recipient, refund account, and fee are understood. [NEAR account APIs](https://docs.near.org/tools/near-api) · [NEAR testnet](https://docs.near.org/integrations/testing) · [NEAR MCP](https://github.com/nearai/near-mcp) · [1Click SDK flow](https://github.com/near/agent-skills/blob/main/skills/near-intents/rules/sdk.md)

## 1. ProofBounty

- **One-line pitch:** A requester posts a small task, two worker agents bid, and a separate reviewer agent releases a verifiable payout to the winning worker.
- **User problem:** Small research or data-cleanup tasks need price discovery and a visible reason for paying one agent over another.
- **Swarm roles:** Requester agent writes a narrow task and escrow cap; two worker agents independently bid and submit a result hash; reviewer agent checks a deterministic acceptance rule (for the demo, extract a specified value from a fixed public JSON endpoint); coordinator agent selects the lowest valid bid and triggers settlement. Each role signs from its own sub-account. The reviewer reports evidence; it does not hold the requester key.
- **NEAR tech in the critical path:** Five real testnet sub-accounts; `near-api-js` signed `post_task`, `bid`, `submit`, `review`, and `settle` calls; a testnet escrow contract that stores the task, bid, result hash, verdict, and payout and releases **testNEAR** to the winner. NEAR MCP lets agents read task state and verify payout transaction/account balance. **Mainnet 1Click leg:** after the same winner is chosen, the requester can execute a tiny actual 1Click swap/payout to that worker's mainnet destination; display quote, deposit hash, and terminal status. This is real Intents settlement on mainnet, separate from the testnet escrow receipt.
- **Minimal end-to-end demo:** Fund the parent and create agent sub-accounts → requester escrows 0.3 testNEAR → workers place different bids and produce outputs → reviewer validates one output against the fixed endpoint → coordinator settles → show contract state, winning worker balance delta, and testnet transaction hashes. If mainnet funded: run a small live 1Click order for the same winner and show its status. A failed review returns escrow to requester; no claimed payout without confirmed chain state.
- **Rough build plan:** H0–1 set up testnet parent, faucet, environment; H2–3 create/fund sub-accounts; H4–5 write task/bid state contract; H6–7 add escrow and settlement/refund; H8–9 deploy and exercise contract manually; H10–11 write agent role prompts and deterministic validator; H12–13 wire signed calls and event log; H14–15 add MCP account/state inspection; H16–17 build one-command demo and failure handling; H18–19 test with fresh accounts and transaction links; H20–21 add live mainnet 1Click adapter if funded; H22–23 record demo, tighten README and secret handling.
- **Main risk:** A reviewer controlled by the demo operator could appear to rubber-stamp submissions. The fixed JSON acceptance check and on-chain reviewer verdict make the behavior inspectable; the tiny mainnet 1Click leg still depends on funding, supported assets, and API availability.

## 2. SwarmCart

- **One-line pitch:** Buyer agents pool tiny commitments, seller agents compete on price, and a coordinator buys only when a group threshold is met.
- **User problem:** Several users want the same paid data or API package but cannot individually justify its price, and collective buying needs fair refunds if the deal fails.
- **Swarm roles:** Two buyer agents decide their maximum contributions; two seller agents submit competing offers for a fixed digital item; an evaluator agent compares price and a supplied content hash; a coordinator agent closes the cheapest valid offer. Every participant uses a distinct NEAR sub-account.
- **NEAR tech in the critical path:** Testnet sub-accounts and signed calls to a small pooled-purchase contract. Buyers deposit **testNEAR**, sellers post offers, and the contract pays the selected seller only if contribution total reaches its price; otherwise buyers invoke refunds. NEAR MCP agents inspect offers, balances, and the final receipt. **Mainnet 1Click leg:** a buyer can make one small real Intents payment to a mainnet seller destination after the testnet group decision; show it as a separate live payment, not as a testnet pool transfer.
- **Minimal end-to-end demo:** Create/fund accounts → sellers offer the same sample data asset at 0.25 and 0.30 testNEAR → two buyers contribute 0.10 and 0.15 → evaluator confirms the lower offer's content hash → coordinator closes → seller balance rises and buyers receive an on-chain purchase receipt; repeat with insufficient contributions and show refunds. If available, run the separate tiny mainnet 1Click payment and show terminal status.
- **Rough build plan:** H0–1 account/faucet setup; H2–3 sub-account creation and keys; H4–5 contract offers and deposits; H6–7 threshold close and refunds; H8–9 deploy/test happy path; H10–11 seller and buyer agent decisions; H12–13 wire signed contract calls; H14–15 MCP reads and receipts; H16–17 full CLI demo; H18–19 refund and duplicate-close checks; H20–21 optional live 1Click leg; H22–23 record demo and clean setup docs.
- **Main risk:** A digital-item hash proves commitment, not usefulness or delivery. Keep the demo item public and fixed, and make the evaluator's hash check explicit. The small mainnet payment cannot claim to settle the testnet pool itself.

## 3. Triangulate

- **One-line pitch:** Three specialist agents independently answer a factual question, challenge one another, and split a reward only when their claims agree with a checkable source.
- **User problem:** A single AI answer can be wrong; paying several agents is wasteful unless disagreements and reward allocation are auditable.
- **Swarm roles:** A finder agent extracts an answer from a fixed public JSON source; a skeptic agent produces an independent answer and a source hash; an adjudicator agent checks both against a deterministic parser and decides whether to split reward, pay one agent, or refund. A requester agent posts the question and reward. Each signs from a separate sub-account.
- **NEAR tech in the critical path:** Four testnet sub-accounts; signed answer-commit and reveal calls; a compact testnet contract escrows **testNEAR**, records commitments and verdict, and splits payouts to matching agents. MCP is used by the skeptic and adjudicator to read the existing commitments and verify final chain receipts. **Mainnet 1Click leg:** requester makes a tiny real swap/payment to a winner's mainnet address through 1Click after the testnet verdict, with quote, deposit, and final status shown separately.
- **Minimal end-to-end demo:** Escrow 0.2 testNEAR on a concrete question such as a field in a pinned public JSON document → finder and skeptic independently commit hashes → reveal answers → adjudicator checks source and signs verdict → contract releases 0.1 testNEAR to each correct agent or refunds on timeout/invalid result → display account balance changes and receipts. Optionally run the live mainnet Intents payment for one winner.
- **Rough build plan:** H0–1 pick stable source and question; H2–3 create/fund testnet sub-accounts; H4–5 contract escrow and commitments; H6–7 reveal, verdict, split/refund; H8–9 deploy and manual calls; H10–11 implement independent finder/skeptic calls; H12–13 deterministic adjudicator; H14–15 MCP reads and signed orchestration; H16–17 end-to-end CLI output; H18–19 timeout/incorrect-answer path; H20–21 optional mainnet 1Click integration; H22–23 fresh-run verification and demo recording.
- **Main risk:** The agents can share the same model error or coordinate off-chain, so independence is limited. Use different prompts/roles and a deterministic source check; do not claim cryptographic proof of AI independence. Mainnet Intents remains a separate optional payment.

## Recommendation

**Build ProofBounty.** Its bids, reviewer decision, escrow, and payout form the clearest agent-to-agent economy for the AI Swarms brief. The winning worker's testnet balance change and contract state give judges a short, code-verifiable end-to-end path. It also offers a natural place to attach a real, small mainnet 1Click settlement if access is ready. Keep the contract limited to task escrow and outcome recording; it is not a replacement for Agent API spending policies.
